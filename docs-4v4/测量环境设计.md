# AIOS 调度实验测量环境设计

日期：2026年11月27日

本文说明测量环境的组成、打点位置、指标定义和自检结果，配合 `docs-4v4/顶尖4v4_AIOS调度优化设计文档.docx` 使用。代码在仓库根目录的 `benchmark/`，运行方式见 `benchmark/README.md`。

## 一、目的

在改动调度器之前，先建立一套能重复运行的测量环境，回答三个问题：

1. 原版在混合负载下，短请求被拖了多久，拖在哪个环节。
2. 每项改动分别消除了哪一段时间，代价是什么。
3. 改动之后并发上限、正确性和通知次数是否符合预期。

环境只替换最底层的模型调用，其余请求路径保持原样。

## 二、请求路径

一次 LLM 请求在原版中的路径：

1. 调用方调用 `SyscallExecutor.execute_llm_syscall`，新建 `Syscall` 线程，设置创建时间，把 syscall 放进全局 LLM 队列，然后阻塞等待。
2. `FIFOScheduler.process_llm_requests` 先等待 `batch_interval`，再不断从队列取请求组成一批。
3. `LLMAdapter.execute_llm_syscalls` 按模型分组，每个模型组一个线程池，组内每个请求一个线程，最终调用模型。
4. 一个模型组全部结束后，结果才逐个写回 syscall 并唤醒调用方。

由此产生两个等待来源：批次边界造成的排队，以及同组统一返回造成的通知延迟。

## 三、组成

### 3.1 假后端

`benchmark/mock_backend.py` 继承 `LLMAdapter`，只覆盖 `_get_model_response`。行为是按请求给定的毫秒数睡眠，然后返回一段固定格式的文本。模型组划分、线程池、结果写回、事件通知全部走原代码。

不在 `litellm.completion` 层打补丁，原因是那样拿不到后端真正返回的时刻，也无法按请求指定耗时。

故障也在这一层注入：

| 故障 | 行为 |
| --- | --- |
| ok | 正常返回 |
| error | 睡眠后抛出普通异常，适配器归类为 500 |
| timeout | 睡眠后抛出带 timeout 字样的异常，适配器归类为 408 |
| slow | 在正常耗时上增加额外延时 |

### 3.2 场景文件

`benchmark/scenario.py` 一次算好每个请求的到达时间、服务时间、故障类型，写成 JSONL。不同策略和不同重复运行共用同一份场景，保证每个请求的耗时一致。

服务时间按模型固定开销、输入 token、输出 token 计算，再乘对数正态抖动。输出 token 从对数正态分布采样，并被 `max_tokens` 截断。配置里也可以直接给固定耗时，用于正确性测试。

### 3.3 负载执行

`benchmark/workload.py` 每个任务一个线程。单步任务发一个请求；多步任务按顺序发请求，上一步返回后等待配置的间隔再发下一步。请求通过真实的 `execute_request` 发出，调用方在阻塞返回的时刻记录时间。

### 3.4 打点

`aios/utils/probe.py` 提供 `emit(event, syscall=None, **fields)`。未安装接收器时只做一次函数调用，开销可以忽略。安装接收器后，事件写入 JSONL。

时间戳统一使用 `time.monotonic()`。

打点位置：

| 文件 | 位置 | 事件 |
| --- | --- | --- |
| `aios/syscall/syscall.py` | 请求进入队列前 | enqueue |
| `aios/scheduler/fifo_scheduler.py` | 抽取批次时 | batch、batch_dispatch |
| `aios/llm_core/adapter.py` | 分组完成后 | grouped |
| `aios/llm_core/adapter.py` | 工作线程开始执行 | exec_start |
| `aios/llm_core/adapter.py` | 结果写回并唤醒 | notify |
| `benchmark/mock_backend.py` | 睡眠前后 | backend_start、backend_done |
| `benchmark/workload.py` | 发起和返回 | arrive、return |

适配器里原本有六处结果写回和通知，已合并到 `_notify_syscall`，保证所有路径的时间戳和事件一致。

### 3.5 指标汇总

`benchmark/metrics.py` 读取事件和场景，算出每个请求的时间分解，再按整体、长短请求、首步和后续步骤、故障类型分组统计。

## 四、指标定义

| 指标 | 计算方式 | 含义 |
| --- | --- | --- |
| enqueue_gap_ms | enqueue - arrive | 发起请求到进入队列的开销 |
| batch_wait_ms | batch - enqueue | 等待被调度器取走 |
| sched_wait_ms | exec_start - batch | 从取走到工作线程真正执行 |
| service_ms | backend_done - exec_start | 后端实际耗时 |
| notify_lag_ms | notify - backend_done | 后端完成到调用方被唤醒 |
| response_ms | return - arrive | 调用方看到的总时长 |
| slowdown | response_ms / service_ms | 相对后端耗时的放大倍数 |

汇总指标包括吞吐量、总完成时间、峰值并发、批次数量与批次大小、错误和丢失数、重复通知数。

长短请求按计划服务时间的中位数划分。

## 五、自检

`python -m benchmark.selftest` 覆盖以下内容：

1. 同一配置两次生成的场景完全一致，服务时间和参数相符。
2. 单请求的七个时间点齐全，且严格单调递增。
3. 同时到达的 12 个请求落在同一批，峰值并发等于 12，短请求出现明显的通知延迟。
4. 5 个三步任务共 15 个请求全部送达，任务级完成数正确。
5. 人为指定错误、超时和正常请求，结果归属正确，每个请求只通知一次，状态码分别为 500、408 和 200。
6. 响应时间不小于服务时间，放大倍数不小于 1。

当前全部通过。

## 六、已知限制

1. 假后端用 `time.sleep` 模拟阻塞，适合比较调度策略，不能代表真实模型的服务时间分布。真实 API 验证需要用同一套指标另外跑。
2. 单步负载可以严格复用到达序列。多步负载的后续步骤到达时间依赖前一步返回，无法完全预生成，只能保证任务启动时间和每个请求的服务时间一致。
3. 原版没有并发上限，几百个请求同时执行时线程数等于请求数。请求规模继续增大需要控制任务线程数。
4. 计时精度受 Python 线程调度影响，毫秒级差异不应当作结论。比较时看均值和 P90 的差距。
5. 适配器里 `_execute_syscall` 使用 `while True`，只有状态为 done 才退出。多数错误路径最终都会写成 done，但模型组线程抛出异常时写入 error，理论上会导致调用方重试不止。搭环境过程中已修正一个 litellm 异常名不兼容的问题，重试上限尚未改动，后续做超时处理时一起处理。
